# دليل ربط وتشغيل MAVI ERP الحقيقي — نقل البيانات الفعلية والتشغيل النهائي (Cutover)

> **الهدف:** تشغيل مشروع MAVI ERP + الشركة الافتراضية على مثيل تشغيل حقيقي مع **نقل بيانات الإنتاج الفعلية** من السيرفر الحالي — بدون لمس السيرفر الحي أبدًا (يظل يعمل ويظل مالك البيانات حتى قرارك بالتبديل).

---

## 0) إزاي المشروع «بيتركب» أصلاً؟ — المستودع × السيرفر × البيانات

سؤال مهم جداً، والإجابة تحسم التشغيل كله:

| العنصر | فين بيعيش؟ | ملاحظات |
|---|---|---|
| **الكود وأدوات التشغيل** | داخل مستودع المشروع على GitHub | كل حاجة أصلًا جوّاه: `Dockerfile`، `render.yaml`، `deploy/docker-compose.yml`، سكربتات التشغيل `scripts/start-*`، أدوات نقل البيانات `src/migration-import.js` + `scripts/verify-backup-file.js` + `src/recover.js`. **مفيش حاجة تتركب برّه المستودع** — أي سيرفر بيسحب المستودع ويشتغل فورًا. |
| **السيرفر / الجهاز** | مكان التشغيل (Render أو VPS أو جهازك) | بيستنسخ المستودع ويشغّل الإعدادات الجاهزة. المستودع هو «المصنع»، والسيرفر هو «المصنع شغّال». |
| **قاعدة البيانات (الطلبات، العميلات، الإيصالات، المال)** | **خارج المستودع تمامًا** | ملف واحد SQLite على قرص السيرفر الدائم (`/data/mavi.db`). مسجل في `.gitignore` (`data/`, `*.db`, `*.db-wal`, `*.db-shm`) **بالتصميم** — الكود يترفع لـ GitHub، أما البيانات الحقيقية فتعتش على القرص الدائم للسيرفر وتتنقل بملفات نسخ احتياطي مُتحقق منها فقط. |
| **السيرفر الحي الحالي (Suga)** | يظل كما هو | إحنا **ما بنلمسوش أبدًا** — بناخد منه نسخة قراءة فقط، والمثيل الجديد بيشتغل بالنسخة. التبديل النهائي قرارك بس. |

**الخلاصة:** نعم — كل أدوات التشغيل والنقل «متركبة» في مستودع المشروع نفسه أصلًا. اللي بيتنقل بين الأجهزة هو الكود (git)، واللي بيتنقل عند تغيير السيرفر هو ملف قاعدة البيانات عبر مسار استعادة مُتحقق منه بالبصمة (الخطوات أدناه).

## 2) اختار مكان التشغيل

### ☁️ الخيار A — Render (الأسهل والأثبت)
1. من حساب Render: **New → Blueprint** واختيار مستودع `mavi-erp-new`.
2. يقرأ `render.yaml` تلقائيًا: قرص دائم 1GB على `/data` + فحص صحة `/healthz` + `SHOW_OTP=0` + `AUTO_SEED=0`.
3. أدخلي متغيرات البيئة الظاهرة بـ `sync: false`:
   - `INITIAL_ADMIN_EMAIL` = إيميل المالكة الحقيقي
   - `INITIAL_ADMIN_PASSWORD` = كلمة مرور قوية جديدة (ليست التجريبية)
4. **مهم:** خلي «Watch Branch» على الفرع التجريبي أثناء التجربة، وبعد موافقتك النهائية اعملي merge إلى `main` وخليه يتابع `main`.
5. Deploy → HTTPS ورابط دائم تلقائيًا.

### 🐳 الخيار B — VPS بـ Docker
```bash
git clone https://github.com/amaarallahamad5-ctrl/mavi-erp-new.git mavi
cd mavi && git checkout arena/c193a50e-mavi-erp-new
INITIAL_ADMIN_EMAIL=<إيميل المالكة> INITIAL_ADMIN_PASSWORD=<كلمة مرور قوية> \
  docker compose -f deploy/docker-compose.yml up -d --build
# HTTPS تلقائي: MAVI_DOMAIN=domain.mavi... ووجّهي DNS → deploy/Caddyfile
```

### 🖥️ الخيار C — جهازك المحلي (تجربة قبل القرار)
- ويندوز: `scripts/start-windows.bat` · ماك/لينكس: `scripts/start-mac-linux.command`
- ينزّل Node.js لو مش موجود ويشغّل على `http://localhost:3000`.

## 3) خد نسخة آمنة من بيانات الإنتاج الحقيقية (قراءة فقط — السيرفر الحي ما يتلمسش)

اختاري طريقة واحدة:

**طريقة أ — من داخل ERP الحالي (الأبسط):**
قسم **«النسخ والأمان»** في لوحة الإدارة → تنزيل النسخة الاحتياطية (ملف `.db`). الخدمة مصممة لتجاهل WAL بشكل آمن وقت التنزيل.

**طريقة ب — من shell السيرفر (قراءة فقط):**
```bash
sqlite3 "file:/data/mavi.db?mode=ro&immutable=0" "VACUUM INTO '/tmp/mavi-export.db'"
sha256sum /tmp/mavi-export.db   # سجّلي البصمة
```

⚠️ **قاعدة صارمة:** أياً كانت الطريقة — عمليات قراءة فقط على السيرفر الحي. لا تعديل ولا استبدال ولا إيقاف.

**أفضل توقيت للنسخة:** وقت أقل نشاط (آخر النهار)، مع إيقاف أي إدخال جديد لدقيقتين أثناء النسخ النهائية إن أمكن — أو اعملي نسختين (استكشافية ثم نهائية قبل التبديل).

---

## 4) تحقّقي من النسخة قبل أي رفع (إلزامي)

```bash
node scripts/verify-backup-file.js /path/to/mavi-export.db --expect-sha256 <البصمة> --json
```
يفحص القراءة فقط: بصمة SHA-256 + سلامة SQLite + جداول MAVI الأساسية + `foreign_key_check` + عدّادات صفوف غير حساسة. **أي فشل = لا رفع، راجعي النسخة.**

---

## 5) ارفعي النسخة على المثيل الجديد (وضع الاستعادة الآمن)

المثيل الجديد (بعد أول تشغيل عادي) يُعاد تشغيله مرة واحدة بوضع الاستعادة — خدمة عربية مدمجة ترفع بالبث المباشر وتفحص وتكتب **ملفاً جديداً مستقلاً** ولا تستبدل الملف النشط أبداً:

```bash
# على السيرفر الجديد (Shell/Console):
MAVI_RESTORE_MODE=1 \
MAVI_RESTORE_SECRET=<رمز عشوائي 32+ حرفاً — يُستخدم مرة واحدة> \
MAVI_RESTORE_TARGET_NAME=mavi-restored.db \
PORT=3000 DB_PATH=/data/mavi.db \
node src/bootstrap.js
```
- افتحي صفحة الاستعادة `http://<السيرفر>:3000/` → اختاري ملف النسخة + الرمز → «رفع النسخة وفحصها».
- أو من الطرفية:
```bash
curl -X POST "http://127.0.0.1:3000/import" \
  -H "Authorization: Bearer <نفس الرمز>" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @mavi-export.db
```
- الحمايات المدمجة: حد 128 MiB (قابل للضبط `MAVI_RESTORE_MAX_MIB`)، فحص مساحة القرص، حد 12 محاولة/10 دقائق، و409 تلقائي عند وجود الملف الهدف (لا استبدال). استجابة النجاح ترجع البصمة في الهيدر `x-mavi-restored-sha256` — قارنيها ببصمة النسخة.

---

## 6) التبديل النهائي (Cutover) وتفعيل الحسابات

1. أوقفي المثيل الجديد، وانقلي الملف المستعيد لمكان `DB_PATH` مع الاحتفاظ بالقاعدة الفارغة القديمة كأرشيف:
```bash
mv /data/mavi.db /data/mavi-empty-$(date +%F).db
mv /data/mavi-restored.db /data/mavi.db
```
2. شغّل المثيل **عادي** (بدون `MAVI_RESTORE_MODE`) — Render/VPS/محلي حسب اختيارك.
3. سجّلي دخول المالكة → افتحي فحص الجاهزية `/readiness` → يجب أن يظل `core_ready: true` مع بياناتك الحقيقية (عدد الطلبات والعميلات يظهر في الفحص).
4. **فوراً** غيّري كلمات مرور جميع الحسابات من داخل اللوحة (يذهب تنبيه readiness الأول).
5. لو ضاعت كلمة مرور في أي وقت (Shell):
```bash
node src/recover.js <إيميل المالكة> "كلمة-مرور-جديدة-قوية"
```

- ☑️ `npm run verify:docker-128m` على Docker حقيقي بحد `--memory=128m` (اختبار الذاكرة الحقيقي، لا يغني عنه نجاح اختبارات Node).
- ☑️ `python3 test/browser-office-ui.py` على متصفح Chromium حقيقي ضد المثيل الجديد (اختبار الواجهة التفاعلية الكامل).
- ☑️ HTTPS فعّال (Render تلقائي / Caddy بالدومين) ونسخ احتياطي يومي مجدول من «النسخ والأمان».

## 8) التراجع الآمن (Rollback) — شبكة الأمان

- السيرفر الحي القديم **يظل شغّالاً** كخطة بديلة — بياناته لم تُمس نهائياً. أي مشكلة حقيقية: وجّهي الفريق للقديم فوراً وأوقفي الإدخال على الجديد.
- الملف المستهدف `mavi-restored.db` مستقل: إعادة محاولة الاستعادة في أي وقت بأمان (امسحي الملف المستهدف أولاً ثم كرري الخطوة 5 برمز جديد).

---

## 9) بعد التشغيل — إدارة الإصدارات القادمة

- أي تحديث جديد: تجربة على الفرع/المعاينة أولاً → موافقتك → merge إلى `main` → Render يعيد النشر تلقائياً مع بقاء `/data` (البيانات تنجو من كل إعادة نشر).
- راجعي تنبيهات `/readiness` بعد كل إصدار، وحافظي على نسخة احتياطية يومية.

> **ملخص القاعدة الذهبية:** الكود في git، البيانات على قرص السيرفر الدائم، النقل بين السيرفرات فقط عبر نسخة مُتحقق من بصمتها عبر وضع الاستعادة، والسيرفر الحي القديم لا يُلمس حتى لحظة التبديل النهائي — وبعدها يظل احتياطاً آمناً.
