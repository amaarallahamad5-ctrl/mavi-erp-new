# دليل التحقق قبل النشر والنسخ الاحتياطي والاستعادة والتراجع (MAVI ERP — `office-*`)

> **تنبيه إلزامي:** هذا الدليل للتنفيذ المعتمد من المالكة فقط بعد استيفاء كافة البوابات المستقلة أدناه. لا تُعد الاختبارات المعملية المحلية بديلاً عن اختبار حاوية Docker الفعلي أو التحقق من إعدادات ونسخ استضافة Suga الحية. يُحظر دمج أي كود في `main` أو النشر أو لمس قاعدة الإنتاج أو إضافة مفاتيح خارجية دون قرار صريح ومستقل.
>
> **أوامر الفحص السريع المرفقة في المستودع:**
> - فحص أي ملف نسخة احتياطية `.db` في وضع قراءة فقط (دون الحاجة لتثبيت `sqlite3` خارجي):
>   `npm run verify:backup -- path/to/mavi-backup.db --expect-sha256 <SHA256>`
> - تشغيل بوابة حاوية Docker الكاملة تحت حد `128m` (على جهاز يتوفر به Docker):
>   `npm run verify:docker-128m`

---

## 1. تهيئة حساب المالكة الأولي بأمان (دون وضع كلمات مرور في سجل الأوامر أو بيئة الخادم الدائم)

وضع كلمة المرور مباشرة في نص أمر `docker run -e INITIAL_ADMIN_PASSWORD=...` قد يتركها في سجل الأوامر (`shell history`) وفي `/proc/<pid>/environ` طوال عمر العملية. المسار الآمن الموصى به يتم على **خطوتين منفصلتين**:

1. إدخال كلمة المرور تفاعلياً في ملف مؤقت بصلاحيات `0600` وتشغيل خطوة التهيئة لمرة واحدة فقط (`MAVI_INIT_OWNER_ONLY=1` — تنشئ الحساب ثم تغلق العملية فوراً):
   ```bash
   mkdir -p /tmp/mavi-docker-vol
   umask 077
   printf "أدخلي كلمة مرور التهيئة (16–128 حرفاً): " && IFS= read -r -s INIT_PW && printf "\n"
   printf "%s\n" "$INIT_PW" > /tmp/mavi-owner.secret
   unset INIT_PW

   docker build -t mavi-erp:staging-check .

   docker run --rm \
     -v /tmp/mavi-docker-vol:/data \
     -v /tmp/mavi-owner.secret:/run/secrets/owner_pw:ro \
     -e NODE_ENV=production \
     -e AUTO_SEED=0 \
     -e MAVI_INIT_OWNER_ONLY=1 \
     -e INITIAL_ADMIN_EMAIL="owner@mavi.eg" \
     -e INITIAL_ADMIN_PASSWORD_FILE="/run/secrets/owner_pw" \
     mavi-erp:staging-check

   rm -f /tmp/mavi-owner.secret
   ```
2. تشغيل حاوية الخادم الدائم تحت سقف `128m` **دون تمرير أي متغير أو ملف لكلمة المرور**:
   ```bash
   docker run --rm -d \
     --name mavi-staging-smoke \
     --memory=128m --memory-swap=128m \
     -p 3100:3000 \
     -v /tmp/mavi-docker-vol:/data \
     -e NODE_ENV=production \
     -e MAVI_STAGING_MODE=1 \
     -e AUTO_SEED=0 \
     -e SHOW_OTP=0 \
     mavi-erp:staging-check

   curl -i http://127.0.0.1:3100/healthz
   curl -i http://127.0.0.1:3100/
   docker stats --no-stream mavi-staging-smoke
   docker stop mavi-staging-smoke
   ```
- **ملاحظة للاستضافة المدارة (مثل Suga / Render):** إذا استُخدم متغير `INITIAL_ADMIN_PASSWORD` من لوحة الاستضافة لتهيئة قاعدة فارغة لأول مرة، يجب **حذف المتغير فوراً من إعدادات الاستضافة ثم إعادة تشغيل/إعادة نشر عملية جديدة**؛ لأن حذف المتغير داخل كود Node وحده لا يمسح `/proc/<pid>/environ` للعملية الأولى على Linux. كما يلزم التأكد خارج المحادثة من إلغاء أي مفتاح أو رمز قديم مكشوف سابقاً.

## 2. بوابة بيئة Staging المعزولة

1. **عزل البيانات والقرص:** يجب أن تعمل بيئة Staging على قرص وقاعدة بيانات منفصلين كلياً عن الإنتاج (بيانات اصطناعية فقط، بلا نسخ بيانات عميلات حقيقيات أو مفاتيح حية).
2. **إعدادات البيئة الإلزامية في Staging:**
   - `NODE_ENV=production`
   - `MAVI_STAGING_MODE=1` *(يفعّل بوابة الدخول `401` و`noindex` ويعطّل قنوات Twilio وWeb Push وGoogle Analytics وOpenRouter)*
   - `AUTO_SEED=0` و`SHOW_OTP=0`
   - يُوصى بالإضافة إلى تعطيل التطبيق لحظر الاتصالات الصادرة (egress) من جدار الاستضافة إن توفر.
3. **التحقق عبر HTTPS:** فتح الرابط عبر `https://` والتحقق من التحويل التلقائي `301` من HTTP ومن وجود `Strict-Transport-Security` وكوكي `Secure; HttpOnly; SameSite=Lax`.

## 3. النسخ الاحتياطي والتحقق المستقل خارج الخادم (قبل أي تحديث مستقبلي)

> **قاعدة صارمة:** مؤشر `last_backup` في لوحة الإدارة يعني فقط أن الخادم أتم إرسال آخر استجابة نسخ من جهته، **ولا يُعتمد عليه وحده كدليل على وجود نسخة احتياطية صالحة**. لا يُعتد بأي نسخة احتياطية إلا بعد حفظها خارج الخادم ومطابقة بصمتها وفحصها وتجربة استعادتها.

1. نزّلي النسخة الاحتياطية من حساب المالكة (`GET /api/admin/system/backup`) وسجّلي قيمة الترويسة `X-Mavi-Backup-Sha256` وحجم الملف.
2. تحققي محلياً على جهاز خارج الخادم من البصمة وسلامة قاعدة البيانات:
   ```bash
   sha256sum mavi-backup-*.db
   sqlite3 mavi-backup-*.db "PRAGMA integrity_check; PRAGMA foreign_key_check; SELECT COUNT(*) FROM orders;"
   ```
   يجب أن تطابق بصمة `sha256sum` قيمة `X-Mavi-Backup-Sha256`، وأن تعيد `integrity_check` القيمة `ok` و`foreign_key_check` صفراً من الصفوف.
3. احتفظي بنسختين منفصلتين على الأقل خارج الخادم مع سجل البصمات والتواريخ.

## 4. الاستعادة بالبث المباشر (`MAVI_RESTORE_MODE=1`) وتخطيط المساحة والأسماء

تكتب خدمة الاستعادة (`src/migration-import.js`) البيانات بالبث المباشر إلى القرص دون تجميع الملف في الذاكرة، وتدعم افتراضياً حتى **`128 MiB`** (قابل للضبط عبر `MAVI_RESTORE_MAX_MIB` بعد التأكد من مساحة القرص)، وتتحقق من توفر مساحة حرة كافية قبل القبول، **ولا تستبدل ملف `DB_PATH` النشط أبداً**:

1. **تخطيط المساحة واسم الملف الهدف:**
   - تأكدي قبل الاستعادة أن القرص الدائم (`/data`) به مساحة حرة تتجاوز ضعف حجم ملف النسخة + `16 MiB` على الأقل لملفات `WAL`.
   - افتراضياً يُحفظ الملف المفحوص باسم `mavi-restored.db`. إذا وُجد ملف سابق بهذا الاسم من استعادة ماضية أو عند تنفيذ تراجع لاحق، حدّدي اسماً جديداً صريحاً عبر `MAVI_RESTORE_TARGET_NAME` (مثل `mavi-restore-20261123.db` — بشرط ألا يطابق اسم `DB_PATH` النشط).
2. **خطوات الرفع والفحص لمرة واحدة:**
   - اضبطي مؤقتاً:
     - `MAVI_RESTORE_MODE=1`
     - `MAVI_RESTORE_SECRET` *(رمز عشوائي سري بطول 32 بايت على الأقل يُولَّد خارج سجل الأوامر)*
     - `MAVI_RESTORE_TARGET_NAME=mavi-restore-YYYYMMDD.db` *(اختياري لتجنب التعارض مع استعادة سابقة)*
   - ارفعي ملف `.db` عبر HTTPS وتأكدي من ظهور رسالة النجاح واسم الملف وبصمة `SHA-256`.
3. **التحويل (`Cutover`):**
   - وجّهي `DB_PATH` إلى المسار الجديد (`/data/mavi-restore-YYYYMMDD.db`)، واحذفي `MAVI_RESTORE_MODE` و`MAVI_RESTORE_SECRET` و`MAVI_RESTORE_TARGET_NAME` من الإعدادات، وأعيدي تشغيل الخدمة وتحققي من الدخول والطلبات والأرصدة والصور.

## 5. خطة التراجع (`Rollback`) وحدودها الواقعية

- **المسار الموصى به أولاً عند أي مشكلة بعد ترقية مستقبلية (التراجع الكامل للكود + لقطة البيانات السابقة):**
  1. الاحتفاظ بملف قاعدة البيانات الأصلي أو لقطة ما قبل الترقية المفحوصة مسبقاً دون حذف.
  2. استعادة لقطة ما قبل الترقية في اسم ملف مستقل جديد (`MAVI_RESTORE_TARGET_NAME=mavi-rollback-YYYYMMDD.db`) وتوجيه `DB_PATH` إليها مع إعادة الكود إلى الإصدار السابق المستقر.
  3. هذا المسار يعيد الكود والبيانات معاً لحالتهما المتطابقة قبل الترقية (مع الانتباه إلى أن أي عمليات أُدخلت بعد أخذ اللقطة لن تكون ضمنها ويلزم حصرها يدوياً قبل التبديل).
- **التراجع للكود فقط على قاعدة بيانات مرقّاة:**
  - جداول `office_*` مستقلة بلا مفاتيح أجنبية عكسية أو Triggers على جداول الطلبات والمدفوعات، وقد نجح فحص smoke أساسي لتشغيل كود `995104c` عليها؛ غير أن التراجع الكودي وحده لا يُفترض كضمان شامل لكل الشاشات دون اختباره مسبقاً على بيئة Staging مطابقة، ولذلك يظل الاحتفاظ بلقطة ما قبل الترقية المفحوصة شرطاً أساسياً قبل أي نشر.

## 6. ضوابط قسم «ملخص يومك والمسودات» (`office-*`) وحدود التحقق المعملي

- **تفعيل قوالب المسؤوليات الـ ١٧ بالكامل بوضع محلي آمن افتراضياً:** جميع أنواع المسودات والكشوفات الـ ١٨ الموزعة على المسؤوليات الـ ١٧ (`10` تشغيلية متاحة للموظف والمالكة بلا أي أرقام مالية، و`8` مالية/تخطيطية/رقابية حصرية للمالكة) تعمل بقوالب اختبار محلية (`fixture` عبر `/worker/step` أو `/worker/drain`) مع `AI_ENABLED=0` و`MAVI_OFFICE_PROVIDER=disabled` افتراضياً؛ **لا يوجد أي إرسال آلي للعميلات ولا نشر إعلانات ولا صرف مالي تلقائي**، والقرار النهائي واعتماد المسودة للمالكة (`owner`) حصراً.
- **منع الاعتماد على بيانات أو صور/إيصالات متقادمة:** يتحقق المحرك بالبايت (`SHA-256` عبر شرائح `64 KiB` محدودة الذاكرة) من صور الموديلات وإيصالات العربون وصور وإيصالات التصميم الخاص عند فتح المسودة الفردية وعند `POST /api/admin/office/jobs/:id/recheck` وعند قرار الاعتماد (`409 stale_subject_facts`)، بينما تعتمد القوائم الجماعية على بصمة ميتاداتا سريعة (`subject_fast_hash` للمالكة و`subject_staff_hash` التشغيلية للموظف بلا كشف للإيصالات أو الأسعار).
- **ربط مباشر داخل شاشات الـ ERP اليومية:** يعمل الفريق مباشرة داخل شاشة تفاصيل الأوردر (`#of-order-ctx-section` عبر `GET /api/admin/office/context/order/:code`)، وكروت موديلات التفصيل (`officeOpenStyleAssistant` عبر `GET /api/admin/office/context/style/:styleId`)، وطلبات التصميم الخاص للمالكة (`officeOpenCustomAssistant` عبر `GET /api/admin/office/context/custom/:requestId`)، مع توليد سريع آمن عبر `POST /api/admin/office/quick-draft` وظهور رابط واتساب اليدوي (`wa.me`) وزر النسخ **بعد الاعتماد البشري من المالكة حصراً (`status === 'approved'`)**.
- **بوابات إلزامية خارج بيئة الاختبار قبل أي تشغيل مستقبلي:** اجتياز اختبارات Node وقياس `/proc/<pid>/status` المعملي لا يغني عن تشغيل `npm run verify:docker-128m` على محرك Docker فعلي (`--memory=128m --memory-swap=128m`) وتشغيل `python3 test/browser-office-ui.py` على متصفح Chromium حقيقي والتحقق من إعدادات HTTPS والنسخ الاحتياطي لقاعدة البيانات على بيئة Staging مستقلة قبل نقل التحديث للـ ERP الحي.
